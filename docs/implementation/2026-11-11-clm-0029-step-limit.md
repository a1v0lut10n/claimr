# CLM-0029: A step limit for queries

## Premise

The accepted record `2026-11-11-step-limit-for-queries.md`: a query may be
given a budget of resolution steps — one iteration of the machine loop,
the count the interrupt poll already keeps, one counter including
sub-searches and table evaluations, for the whole query across its
answers. Reaching it is an ordinary runtime error naming the count and
the goal about to be resolved. Unlimited by default; `--steps N` and
`:steps N` (0 = unlimited) set it; `Solutions::with_step_limit(n)` in the
API. The check is exact and one comparison.

## Shape of the implementation

**Machine.** `Solutions` gains `step_limit: Option<u64>`, the builder
`with_step_limit(n)` and the accessor `steps()` (the count so far, which
the exact-count test reads). `check_interrupt` becomes `account_step`: it
increments the count, stops with `EvalError::StepLimit` when the count
exceeds the budget, and polls the interrupt flag every 256 steps as
before. The error's `goal` is the head of the goal list at that moment,
rendered with the query's variable names: a pending call or a tabled
abstract call is built in the store and rendered by `render_one` (the
query stops, so the allocation is harmless); a pending constraint goal, a
commit, a collection or a table-answer goal is named by kind; an empty
list is "an answer". `interrupted()` stays false.

**Error.** `EvalError::StepLimit { steps, goal }`, Display:
`step limit of N reached at GOAL; the query may not terminate (an untabled
recursion over cyclic data?) — raise the limit, or table the predicate`.
No span.

**CLI.** `--steps N` parsed like `--limit` (a `u64`), applied to both batch
paths through the builder, and passed to `Repl::new` to seed `:steps`.
Batch behaviour is the existing runtime-error path: answers already printed
stand, the error goes to stderr with the query, exit 1; `--json` emits the
query's error document in the existing shape.

**REPL.** `steps: Option<u64>`, `:steps N` (0 = unlimited) beside `:limit`,
a line in `:help`, the builder applied in `answer`; the existing `None`
arm prints the error after the answers and keeps the session.

   are yielded, then the error; `interrupted()` false. Integration: batch

5. Docs: `evaluator.md` (the budget beside the interrupt),

   runtime-error section, shape unchanged), README (flag and command),
   architecture README (`cli` row); this plan.

## Findings

- **The REPL echoes a piped query.** The pipe-driven REPL prints the query
  line before its answers, which the new REPL test first forgot; nothing to
  change, noted for the next test written against a pipe.
- **The goal named is the next one, not the last.** The budget is checked
  before a step is taken, so the error names the goal the machine was about
  to resolve (`anc(a, _1)` for the left recursion, `loop(X)` for the
  generator), rendered with the query's variable names where the goal is a
  call; a constraint or control goal is named by kind rather than rendered,
  since the message is a pointer, not an explanation.
